  • Plan: implementation plan.
  • Architecture: source, build, install and consumer pipeline.
  • Author / date: GitHub Copilot for @lucioctinoco, 2026-10-16.
  • Baseline: 269f962e6dcd47d7464a73c24d7fdeec1ae3390b.
  • Not done yet: no code written, Verus not installed or run.

Summary

A developer chooses to have one specific claim about their Rust code checked by Verus. Here is how it works:

  1. A reviewer confirms that the claim, written in English and as a formal

contract, says the right thing.

  1. A small local helper runs one tested version of Verus on the selected code.
  2. The helper saves a record of exactly what was checked and what happened.
  3. The result appears in the existing Proof Pack.
  4. Before anyone relies on the result, the helper checks that the code, contract,

tools and settings still match what was checked.

The first demonstration is a tiny function that checks whether a requested range fits inside a buffer. It is not OpenVMM. We must see correct code pass and deliberately broken code fail. A passing check never replaces existing tests and never approves a whole feature.

Scope status. Tim merged the specification unchanged, but its own text says implementation waits for his scope decision. This draft is for that review. It keeps the specification's synthetic example rather than reopening the choice. Installing tools and production work still need separate permission.

Terms

  • Verus: a tool that mathematically checks Rust code against a written contract.
  • Contract: a precise statement of what a function must do.
  • Obligation: one claim the verifier is asked to check.
  • Attempt: one run of the verifier (or one decision not to run it), with its record.
  • Manifest: the saved record of one attempt.
  • Trust declaration: the list of things the check assumes but does not

prove, such as the correctness of the Rust compiler.

  • Applicability: whether an old result still applies to the current code:

current, stale (something it checked has changed) or unknown (we cannot tell).

  • Qualification: testing one exact Verus version in one approved

environment before relying on it.

  • Digest: a SHA-256 fingerprint of a file's exact contents.

Responsibility

This component does one thing: it turns one chosen, reviewed claim into evidence that the existing Proof Pack can use.

It does not add an orchestrator, model provider, proof service, database, new reviewer panel or upload path.

First slice: one example function, one contract, one approved local environment, saved attempt records, and a real acceptance check in the Proof Pack. Tests may simulate the verifier's output, but a live Verus run must show that the simulations match real behavior.

Off by default. When nobody opts in, the existing design and implementation workflows do not look for, install or run Verus. They create no extra files and add no reviewers. Verification guidance loads only after someone chooses it. Declining leaves the normal workflow unchanged.

Data shapes

The attempt is the central record. Each attempt gets its own ID, separate from its outcome. Everything in one attempt (code, contract, obligations, trust declaration, command and output) refers to the same snapshot of the code. An attempt cannot declare itself accepted.

Supporting values: the obligation ID, the list of files checked, the tested toolchain ID, file digests and the trust declaration. Requirements and reviewers are referenced by ID, not copied.

Storage. Each attempt writes one final manifest plus a limited amount of diagnostic output. These are plain files, not a database or a second ledger. This includes attempts that stopped before running Verus. An interrupted attempt leaves only private temporary files, which can never be accepted. Saved records are never edited later, for example to change "passed" to "failed".

Applicability is calculated when the result is used, never stored. A saved accepted: true flag could outlive the inputs it described, so there isn't one.

Review approval is a separate input. It is tied to the exact content of: the English obligation, the requirement it comes from, the formal contract and the trust declaration. Matching IDs are not enough, because the wording behind an ID can change. Product acceptance remains the job of the existing checks.

Other rules:

  • Durations can be added up only for runs that did not overlap.
  • Outcomes and applicability are categories; they cannot be added up.
  • A correction or retry creates a new attempt; it never overwrites an old one.
  • There is no existing evidence format to migrate. A decision record (ADR) and

compatibility tests are required before this format is accepted.

The Example Function

Proposed interface (not yet compiled or tested): validate_range(buffer_len, offset, length) -> optional (start, end). It uses the target platform's unsigned machine-sized integer. It checks a range against a buffer length. It does not allocate or read memory, authorize access, or prove anything about later I/O.

A range is valid when all three of these are true:

aligned(offset) := offset mod 4 = 0
valid := aligned(offset) AND offset <= buffer_len
         AND length <= buffer_len - offset

These definitions are mathematical, so they cannot overflow. In the code, the subtraction happens only after confirming offset <= buffer_len, so it cannot underflow either.

  • The offset must be a multiple of four. This is a rule of the example, not of Verus.
  • The length can be any value.
  • Empty ranges are allowed at any aligned offset up to the end of the buffer,

including offset zero of an empty buffer.

What the contract requires:

  1. The function returns a range if and only if the input is valid. The

"if" half stops a function that rejects everything from passing.

  1. A returned range is exactly (offset, offset + length).
  2. The range's end is at most buffer_len.
  3. No arithmetic in the code overflows.

The contract covers every possible input; it does not exclude bad ones.

Input (buffer_len, offset, length)Required resultWhy
(16, 4, 12)Accept (4, 16)Ends exactly at the buffer's end
(16, 4, 13)RejectOne byte past the end
(16, 3, 1)RejectOffset not a multiple of four
(16, 20, 0)RejectOffset outside the buffer
(0, 0, 0)Accept (0, 0)Empty range in an empty buffer
(16, 16, 0)Accept (16, 16)Empty range at the end
(MAX, 0, MAX)Accept (0, MAX)Largest values, no overflow
(MAX, MAX - 3, 4)RejectEnd would overflow (on 32- and 64-bit targets)

Deliberate bugs for the demonstration:

  • Change only the code's comparison from length <= buffer_len - offset to

<. The exact-end input (16, 4, 12) is then wrongly rejected, so the unchanged contract must fail.

  • Separately, make the code accept an out-of-bounds range. The safety part of

the contract must fail.

Never change the contract, trust declaration or selected obligations to make the demonstration pass or fail.

Verus syntax, proof helpers and build commands are deliberately left out. The qualification experiment must establish them for the exact version used.

Contracts

Operations (not yet a command-line interface)

The helper does three things:

  1. Run a reviewed attempt.
  2. Assess whether its evidence still applies.
  3. Report the result.

These can live in one Python module in the pack. No service or plugin interface is needed. Command names wait until after the experiment.

Inputs to a run: explicit opt-in, repository root, one reviewed obligation and trust declaration, a single source file, the tested toolchain ID, an approved fixed command, and finite resource limits.

Rejected before running: paths outside the repository, symbolic links and other non-regular files, duplicate IDs, incomplete reviews and untested commands.

How Evidence Is Accepted

Pinning down exactly what was checked

Version 1 supports a single self-contained source file and a fixed, reviewed library baseline. Cargo workspaces, build scripts, external macros and unknown dependencies are unsupported until we can record everything they pull in. Code in other languages is never silently rewritten in Rust.

Steps:

  1. Create a private temporary directory unique to the attempt.
  2. Read the source file once, take its digest, and run Verus on that copy.
  3. Confirm, using the tested version's output, that this exact copy and these

obligations were checked, and that no option turned checking off.

  1. Record the full set of library, toolchain, solver, setting and target

versions under the toolchain ID. If any is unknown, there is no current evidence.

The copy and environment must not change during the run. Comparing digests before and after is not enough, because a file could change and change back mid-run. If the approved environment cannot guarantee this, stop qualification and say so. Unpinned dependencies from the surrounding system are rejected.

The acceptance check

Evidence counts only when all of these are true:

historical outcome is passed
AND the manifest and required diagnostics are complete and their digests match
AND the intended obligations were checked, as confirmed by the tested version's output
AND the reviewed obligation, requirement, contract and trust declaration match the recorded digests
AND the current inputs and environment match the checked ones
AND the existing required tests, reviews and permissions are satisfied

This check is what decides acceptance. Reading or displaying a manifest does not.

  • An assessment applies only to the exact code tree it checked. If anything

relevant changes afterwards, it must be re-run.

  • A timestamp or branch name does not identify inputs.
  • A hand-edited "passed" record is not verifier evidence. Anyone with write

access to the repository is trusted, so reviewers rely on reproducible runs. Version 1 does not claim cryptographic attestation.

Applicability rules:

  • A known change to a checked input makes the result stale.
  • Missing information, missing or corrupt evidence, or any other inability

to compare makes it unknown.

  • Only a complete, exact match is current.
  • Any outcome other than passed is never eligible, whatever its applicability.
  • The original outcome always stays visible.

Patterns

  • One adapter for Verus: a single version-specific boundary separates raw

process output from acceptance decisions. No registry for multiple verifiers.

  • Write-once records: one final record per attempt. No event-sourcing framework.
  • Calculated applicability: worked out from current inputs, never stored as a flag.

Smallest solution that works: the feature only runs after opt-in. It reuses the Proof Pack, existing roles and run_bounded, and uses Python's standard library for hashing, JSON and files. No new dependency or database is justified. Existing private atomic-write helpers show precedent but are not assumed to be reusable public APIs. The experiment picks the simplest write-without-overwrite method it can actually demonstrate.

Error & concurrency model

OutcomeMeaning
passedThe tested Verus version's output confirms the intended obligations and safety checks succeeded. A zero exit code alone is not enough.
failedVerus output shows a declared obligation or safety condition was not met.
inconclusiveNo conclusion was possible: timeout, crash, output too large, malformed or unknown output, or failed containment or cleanup.
unavailableThe approved tool or permission to run it is missing.
unsupportedThe target, dependencies, version or required limits cannot be supported.
cancelledSomeone cancelled the run. Later success output cannot override this.
not-runThe attempt was planned or withdrawn and Verus never ran.
  • Cancellation, timeout, resource-limit and cleanup failures take priority

over output that looks like a pass.

  • No automatic retries and no automatic proof repair. A retry is a new, explicit attempt.
  • If the meaning or the trust declaration changes, the claim goes back for

review. Withdrawing a claim is recorded, but it is not a proof.

  • Attempts that never ran Verus have no invented output or duration.

Concurrency:

  • Only one attempt at a time may write to an evidence folder; others are refused.
  • Separate worktrees that share an evidence folder must agree on its identity.
  • If a previous owner seems to have died, report it for manual recovery.

Never take over silently.

  • A finished record is published once from private temporary files and never

overwrites an existing attempt, even in a race.

  • An interrupted or unverifiable publish leaves no acceptable evidence.

UI & interaction design

Where it appears: the existing conversation and Markdown output. No new visual interface, design tokens, DESIGN.md or images. Status never depends on color. Command names wait for the experiment.

Example report (illustrative; not a real result):

Outcome: passed | Obligation: descriptor-range-v1 | Applicability: stale
Not eligible for current acceptance: source identity changed.
Historical scope: synthetic descriptor validator, <recorded target/toolchain>.
Contract and trust: <review references and identities>.
Evidence: <repository-relative reviewed evidence reference>.
Not established: memory authorization, downstream I/O, whole-feature correctness.
Next action: re-run the unchanged reviewed obligation for the current inputs.

States:

  • Off or declined: the normal workflow continues.
  • First use: explains what setup is missing.
  • Running: shows that a time-limited attempt is in progress.
  • Nothing selected: a clear input error.
  • Finished: every outcome gives a reason and a next action.
  • Stale or unknown: shown next to the original outcome.

Long diagnostics are cut off with a visible notice. If cutting them off makes the result unreadable, the outcome is inconclusive. No animations, hover-only information, custom keyboard controls or new dashboard. Review of the contract and trust declaration happens before running and before acceptance, and any change in meaning sends it back.

Telemetry

  • One local formal_verification.attempt span per request. Its ID follows the

attempt through snapshot, run, publish and acceptance.

  • Events: requested, rejected before running, launched, completed, publish

incomplete, acceptance assessed. Reason codes are listed in the failure table.

  • Counters come from final outcomes. Duration is recorded only when Verus actually ran.
  • Output size and number of checked obligations show volume. This helper does

not use a language model, so no token or cost data is recorded.

  • Uses the repository's existing logging conventions and Python's standard

library. No tracing backend or new SDK is needed.

  • There is no HTTP interface, so the RFC 9457 error format does not apply.
  • Tests confirm the attempt ID, reason and duration are present or absent as

expected, output is limited, and no planted secret or home path appears in the public report.

Before the Live Experiment

Fill in and review these before any live run:

  • operating system and CPU architecture;
  • Verus release and download digest;
  • Rust, library and solver versions;
  • target and settings;
  • the approved isolation method;
  • time, memory, process and output limits;
  • the selected obligation, and who reviews the contract and trust declaration;
  • how the snapshot is kept unchanged.

None of these has been decided yet.

What the experiment must show: the real code is checked directly; exactly which obligations were checked; which assumptions are trusted; the correct version passes and the buggy one fails; the output format; that limits are actually enforced; that no outside dependency changes the result; and that the run can be reproduced. Publish only reviewed, size-limited evidence.

If the chosen Verus version cannot show what was checked and what was trusted, report the gap and revise the design. Do not build a general-purpose parser to paper over it.

Conformance notes

The pack stays a source, build and install pipeline. It does not become a Rust application or a model-routing runtime, and no new runtime archetype is added. The record format, helper location, alignment rule and resource policy are proposals [Inferred], not approved decisions or observed behavior.

Flagged risks & residual unknowns

  • Known from reading [Verified]: the repository code and the Verus

documentation cited above. These are observations of source and documentation, not of behavior.

  • Not yet known [Flagged]: whether Verus checks the right code correctly,

how to read its output, whether checked code matches compiled code, the full set of toolchain inputs, isolation, file-publishing behavior and Windows support.

  • Digests show that files did not change. They do not show that a contract

says the right thing.

  • Human review of the claim and trust declaration, and the existing tests,

remain essential.

Gate record

An independent Astra (gpt-6-astra) review returned REVISE with one major finding: matching obligation IDs did not prove the reviewed English meaning was unchanged. The fix ties review approval to the content of the English obligation and its requirement, in the manifest, the acceptance check and the tests. A separate Astra recheck confirmed the finding resolved. Other design gates remain open. No veto was cleared by the author, and no live proof is claimed.
