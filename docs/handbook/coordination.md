# Coordinate work without losing ownership

Several agents can finish independent work faster, but they can also make a repository less trustworthy. Two sessions can edit the same file, regenerate the same derived output, answer each other's questions in private, or report “done” without returning the evidence the owner needed. AI-Forward coordination is the method for dividing work while keeping one accountable owner, one visible plan and one reviewed join.

Use coordination when the work is large enough to split into independent tracks and the split itself is safer than one coherent session. Do not use it because a task feels important. Many tasks are best handled by one agent with full context, especially when the design is unsettled or each decision changes the next decision.

## Start with one owner

The **Owner** is the person or session that remains accountable for the outcome. The Owner decides scope, accepts or rejects decisions, and integrates the tracks. The **Coordinator** is the operating role that turns the plan into assigned work, watches seams, receives evidence and joins the result. Often they are the same session. A **worker** owns one track in one worktree and returns the evidence named in the plan.

The Owner does not have to write every line. The Owner does have to decide what counts as success and what must stop for review.

## When one agent is better

Stay with one agent when:

- the interface or data contract is not settled;
- the same files would be authored by every track;
- the task is mostly reasoning, not independent implementation;
- you cannot state each track's exit evidence;
- harness setup would take more effort than the work.

For HarborTasks CSV export, do not split immediately after the sentence “add export.” First decide the export contract: all matching tasks or visible rows, which fields are authorized, and what empty results look like. Until that contract is fixed, backend and UI work change each other's shape.

## When coordination earns its cost

Coordinate when tracks have real independence. A good split has no data dependency, no decision dependency and no shared authored file. It also has a reason to pay the extra cost: isolation, long-running machine time, context hygiene, or genuine parallel work.

For HarborTasks, a sensible plan might keep the shared export schema serial, then split into two tracks:

- **export backend** owns the query, authorization, CSV serialization and service tests;
- **export UI** owns the button, loading/error states, empty-state copy and the downloaded-file affordance.

The shared schema is not edited by both tracks. The backend owns it first; the UI depends on it. If the UI needs another column, it sends a seam request rather than editing the backend contract.

## Prepare the plan before launching workers

Use the preparation skill to classify artifacts and write the contract:

```text
/prepare-for-coordination Plan the HarborTasks CSV export work. Keep the export
schema serial, then split backend and UI only if their authored files and evidence
are independent.
```

In Codex, select `$prepare-for-coordination` and give the same request. The produced plan is a document, not a chat memory. It names artifact classes, tracks, the serial spine, seams, struck tracks and order of operations.

Illustrative track row:

```text
track: export-backend
owns: src/Exports/*, tests/Exports/*
depends on: export schema decision
budget: 25 tool calls / 45 minutes
exit evidence: seeded case exports 63 matching rows, unauthorized fields absent,
empty result returns headers
harness: Copilot profile qualified for this repo, or human brief fallback
```

If the preparation step recommends one track, accept that. A plan that deletes unnecessary tracks is working.

## Understand the plain-language tools underneath

The coordination layer is a set of repository scripts and records. You do not need
to memorize their internals, but you should understand what they mean:

- **worktree commands** create isolated checkouts so each worker has its own files;
- **artifact classification** tells Git and the coordinator which files are authored
  by one owner, generated from sources, or append-only registers;
- **mail commands** carry pointers between sessions;
- **request commands** record seam requests and decision requests;
- **ruling commands** append the Owner's decision to a durable note;
- **join commands** integrate track branches and run the gates at the merge point.

Those records are deliberately boring. They make coordination reviewable after the
chat window is gone. When a worker says “I sent the request,” the coordinator can
read the request store. When the Owner rules, the ruling is in a file, not in a
private side conversation.

## Choose an execution mode

Run the execution skill against the plan:

```text
/execute-with-coordination --brief docs/coordination/harbortasks-export.md
```

Use `--brief` when humans will start the sessions themselves, possibly across harnesses. It prints self-contained briefs for each track. Use `--agents` when the current harness can spawn qualified worker sessions in separate worktrees. Use `--launch` only when the native runner profile has been qualified on the current machine and repo. A launch script preparing processes is not proof that permissions, hooks, instructions and model selection were enforced.

The plan does not change between modes. Only the delivery mechanism changes.

If your harness cannot launch workers directly, `--brief` gives you a practical
fallback: start separate sessions in their assigned worktrees and paste each one's
self-contained track brief into it. A **brief** is the full task instruction packet,
including scope, ownership, limits and what the worker must return.

## Worktrees, paths and budgets

Each worker gets its own worktree and branch named for the work. A worktree isolates files, not context; if the task changes, start a new session or compact deliberately. Workers use absolute paths inside their assigned tree. They do not enter another tree, install the coordination layer again, or claim append-only registers.

Every brief should name:

- goal and done-when;
- not-in-scope;
- authored paths owned by the track;
- budget and context ceiling;
- convergence condition;
- exit evidence;
- fallback if the worker cannot proceed.

A budget firing is not permission to continue quietly. It is a signal that the estimate or split was wrong. The worker returns what it has and the Coordinator decides whether to narrow, continue, or stop.

## Messages are not completion

Coordination messages carry pointers and decisions. An acknowledgement means “I received this message,” not “I accept the work,” “I completed the track,” or “the evidence passed.”

Use explicit seam and decision messages:

- **request**: “UI needs the exported filename rule.”
- **ruling**: “Use project slug plus UTC date; backend owns the helper.”
- **receipt**: “Backend returned evidence in commit `abc123`.”
- **acceptance**: the Owner inspected the evidence and accepted it.

Keep receipt and acceptance separate. A worker can honestly return evidence that the Owner rejects.

Permissions follow the same rule. A permission prompt or once-only edit approval is
not a design approval. It only says the host may perform that specific operation.
The Owner still decides whether the operation belongs in the plan and whether its
result is acceptable.

## Join and recovery

Join dependency order matters. Upstream tracks land first; downstream tracks rebase. The join verifies conflict markers, regenerates derived artifacts, runs the integrated checks and only then commits the join.

If two tracks collide on an authored file, do not delete a worktree to resolve it. The collision is evidence that the boundary was wrong. Stop, decide which track owns the file, and turn the other edit into a seam request or a follow-up.

If a worker is silent, use the recorded budget and deadline. Send a clear pointer first. If it still does not converge, escalate to the Owner decision instead of sending longer reminders. A non-converging coordination loop is a plan problem.

If a worker returns partial evidence because a budget fired, do not mark the track
complete. Decide whether to narrow the remaining work, assign a follow-up, or bring
the work back into the serial spine. If a generated file conflicts, regenerate it
from its source rather than hand-merging both outputs. If a register has two new
entries for the same decision, ask which single ruling or note should remain.

## What to review before continuing

Before launching, review:

- whether each track has a real independent exit condition;
- whether all shared schemas, vocabulary and generated outputs are serial or derived;
- whether harness capability is qualified as enforced, observed-only or unsupported;
- whether each worker has a fallback brief;
- whether the Owner is named for decisions.

Before joining, review the returned evidence yourself. A worker report is a lead, not authority.
