The organising idea: an awake/asleep loop

Every self-improving-agent design in the field — whatever it calls itself — splits into two phases. Capture is easy and cheap; consolidation is where the value is. A write-only log rots into “duplicates, contradictions, and stale entries” (Claude Dreams’ own words). The dreaming pass is what keeps it useful.

Online · continuous · high-noise

AWAKE — capture

The agent acts and records what happened.

  • audit log · change log
  • session transcripts
  • simplify: / assume: markers
  • outcome signal (did it work?)
↓ dream ↓
consolidate
↑ ground ↑
Offline · periodic · high-signal

ASLEEP — consolidate (“dream”)

A scheduled pass distils the raw history.

  • dedupe · resolve contradictions
  • compress many instances → a few rules
  • surface cross-cutting classes
  • promote → a durable, linked store
Named by analogy to sleep. When humans sleep the brain replays the day, keeps the signal, discards the noise, and moves short-term memory to long-term. “Dreaming” runs that offline pass over an agent’s session history. It is memory curation — explicitly not model retraining.

The techniques landscape

Two shipping products, three foundational papers, one practitioner trend, and the ops culture that got here first. Each cell of the confidence label: Verified Inferred Flagged.

Claude Dreams product · preview

Async job: a memory store + 1–100 session transcripts → a new reorganised store. Duplicates merged, stale entries replaced, insights surfaced. Steer with an instructions field. Input never mutated → review & discard.

Borrow: the review-and-discard shape. Reject: the vendor runtime store — our store is committed Markdown.
Verified

OpenClaw memory-core product · local

File-based dreaming: light → REM → deep phases; only deep writes durable memory, behind score/recall/diversity gates + a provenance taint gate. Keeps a Dream Diary, stores a preimage, requires source refs, nightly cron.

Borrow: almost everything — it is the closest design to what we need.
Verified

Reflexion paper · 2023

Actor → Evaluator → Reflector. A failure signal becomes a textual lesson stored in episodic memory and re-injected next attempt. No weight update. 91% vs 80% pass@1 on HumanEval.

Borrow: the outcome/Evaluator signal — a log is only mine-able if it records whether the action worked.
Verified · arXiv:2303.11366

Generative Agents paper · 2023

A memory stream + periodic reflection (synthesise higher-level inferences), retrieved by importance × recency × relevance. OpenClaw’s six weighted signals descend from this.

Borrow: the scoring maths for which candidate deserves promotion.
Verified · arXiv:2304.03442

A-MEM paper · 2025

Zettelkasten agentic memory: typed notes, auto bi-directional links, memory that evolves as new notes arrive. A self-organising note graph.

Borrow: nothing new — this is our knowledge graph (V2 frontmatter + typed links + glossary). We already built the wiki.
Verified paper · Flagged numbers

Karpathy’s “LLM wiki” thesis · 2026

Agents collaboratively maintain a Markdown knowledge base — ingest, summarise, cross-ref, refactor. “Context = RAM, LLM = CPU, memory = disk.” Dreaming = the refactor step; dreams fight overfitting by generalising.

Borrow: the mental model. Flag: the overfitting analogy is neuroscience, not proof about LLMs.
Verified pattern · Flagged specifics

Self-improving AGENTS.md trend · 2025–26

Agents append “learnings” to a steering file; some auto-generate them and open a PR; cross-project patterns migrate via <org>/.agent-memory/. Universal rule: never auto-approve — review via PR.

Borrow: the cross-project half + the never-auto-merge guardrail.
Verified trend

SRE & NASA lessons-learned ops culture

Blameless postmortems; a central searchable KB tagged by failure mode; recurrence as the effectiveness metric; NASA’s Collect → Record → Disseminate → Apply lifecycle.

Borrow: capture is worthless without dissemination + application — that is federation.
Verified
The theory tying it together — sleep-time compute (arXiv:2504.13171): spending compute offline, between queries to pre-consolidate context is the warrant for making dreaming a scheduled job rather than an inline step.

The one-sentence gap: AI-Forward has best-in-class capture, classification, and a linked note graph — all in committed Markdown with a human in the loop — but it consolidates one defect at a time and never shares across repos. Add the dream pass (bulk offline consolidation) and federation (share the class, everywhere).

The dream pass, concretely

Borrowing OpenClaw’s three-phase model, mapped onto AI-Forward’s corpus. The deterministic steps (stage, score, taint-gate) are stdlib scripts over JSONL; only the reflect/consolidate step needs a model — keeping the pass cheap, auditable, and mostly reproducible.

Phase 1

Light — stage

  • read the audit + change logs, recent session exhaust, triggered assume:/simplify: markers
  • dedupe raw signals; attach outcome + provenance
  • run scrub.py; drop untrusted/tool-authored origins
writes durable memory: NO
Phase 2

REM — reflect

  • cluster staged signals into recurring themes
  • abstract instance → candidate class (the value step)
  • note contradictions with the existing register/graph
writes durable memory: NO
Phase 3

Deep — promote

  • score candidates (relevance/frequency/diversity/recency/recurrence)
  • gate: score + recall-count + query-diversity must all pass
  • emit proposals (register entries + controls + doc edits) as a reviewable diff + Dream Diary
writes: a PROPOSAL branch — human accepts
The promotion target is a control, not a note. A dream pass that emits prose has done nothing (CI6). Deep-phase output climbs the control ladder: make it impossible → automated control → always-loaded instruction → knowledge doc → register entry — and a proposed control must be shown failing on the un-fixed code before it counts.

How the audit log must evolve

Today the audit log is a write-only history — excellent for grounding, unused as a corpus. To feed a dream pass it must become a mined corpus. Four additions, each named by a source.

  1. A trustworthy outcome signal (Reflexion’s Evaluator). The outcome field exists but is self-reported and optimistic. Enrich it with independent signal — CI pass/fail, whether a fix later got reverted, whether a defect re-referenced the same area. the promotion oracle
  2. Session-transcript ingestion, redacted & taint-gated (OpenClaw). Ingest only interactive, redacted sessions; structurally exclude cron/subagent/tool-output/untrusted origins before consolidation — removal, not a score penalty.
  3. A promotion pipeline with deterministic thresholds (Generative Agents / OpenClaw). Score, then gate on score + recall-count + diversity as an AND — so one-off noise never reaches durable memory.
  4. A Dream Diary (OpenClaw). A human-readable narrative of what each pass added/merged/superseded, kept separate from the durable store and excluded from being re-ingested — or the corpus poisons itself.
Do not touch the source of truth. The JSONL logs stay append-only and immutable; a pass reads them and writes elsewhere (a proposal branch, a Diary). This mirrors Claude Dreams’ “input never modified” and the pack’s own append-only stance — reversibility is the whole point.

Federation: share the learning across every repo

The user’s actual ask — “run against all my local repos and share the knowledge so they all benefit.” This is NASA’s Collect → Record → Disseminate → Apply, and CI8 (“raise it upstream”) done systematically and in both directions.

Each repo → the fleet store

A repo’s dream pass contributes:

  • the generalised class (instance stripped away)
  • its named control (test/lint/instruction)
  • PII/secret-scrubbed, provenance-labelled
→ contribute →
fleet learnings store
← pull at grounding ←

The fleet store → every repo

Every repo pulls at grounding:

  • a mistake made once in repo A …
  • … becomes a control available everywhere
  • general, control-bearing classes ship via /extendaibundle
The federation guardrail (the highest-risk surface): nothing crosses a repo boundary until it is abstracted to a class (no path, no name, no transcript) and PII/secret-scrubbed. The shared item is a shape + a control, never a raw instance. The Privacy lens holds a veto here.

Where does the fleet store live? OPEN

  • The AI-Forward pack itself (via /extendaibundle) — general, control-bearing classes become pack changes, so tests & lints ship to every installed repo for free. Heavier to change.
  • A dedicated learnings/ repo (submodule / synced by the job) — lighter, but ships prose unless paired with the pack for the controls.
  • Likely answer: both — general control-bearing classes → the pack; repo-specific or still-prose learnings → a local learnings/ store. To decide in /specify.

One capability, three faces

The same consolidation pass, exposed three ways — matching how the user framed it (“a skill and a job that can run in claude-cowork / OpenClaw”).

/dream skill interactive

A human runs (or reviews) an on-demand pass over this repo’s corpus. Emits proposals + a Diary entry as a reviewable diff — never an auto-commit. It is class → sweep → derive → prevent run in bulk instead of one defect at a time.

Lead: Domain Researcher (evidence) + Simplifier (strike noise) + Test Architect (a lesson isn’t done until it’s a control).

dream job scheduled · per repo

The same pass wired to run offline on a schedule (cron / GitHub Action / claude-cowork / OpenClaw), opening a branch/PR of proposals per repo. Threshold- or schedule-triggered; bounded input window; throttled model call.

Ships: the deterministic harness + prompts; the model call belongs to the runner (same call the pack made for CLI/doctor).

federation fleet · cross-repo

Each job contributes generalised, scrubbed classes to a central store and pulls from it at grounding — so learnings compound across the whole fleet, not just within one repo.

The user’s core ask. Collect → Record → Disseminate → Apply, automated and two-way.
What NOT to build (the Simplifier’s standing veto): not a vector DB, not a runtime memory service, not a model fine-tune, not a dependency-heavy framework. We already have the note graph, the append-only history, the class register, and the grounding habit. This is a consolidation pass over artifacts that already exist — stdlib scripts + a skill + a schedulable job. Nothing more.

The non-negotiable guardrails

Self-improving loops degrade without these and are bounded with them. Every source independently arrives at the same list — and it is the same list the pack already enforces.

  • Never auto-merge a learning. Every promotion is a PR/diff a human accepts. (Claude Dreams’ discard-model · self-improving-AGENTS.md · BoK D3.)
  • Never mutate the source of truth in place. Emit a new artifact; keep inputs append-only; store a preimage. (Dreaming emits a new store · append-only JSONL.)
  • Never promote untrusted content. A structural taint gate + scrub.py run before consolidation — removal, not a penalty. (OpenClaw · AL4.)
  • Provenance + confidence on every promoted item. Source: file#Lx-Ly or the al-/cl- id, and Verified/Inferred/Flagged. (OpenClaw source-refs · BoK §III.1.)
  • A control is not a control until observed failing on the un-fixed code. Red-first, or it doesn’t count. (CI6.)
  • Federation abstracts to the class and strips specifics. No raw instance, path, name, or token crosses a repo boundary. (Minimisation · Privacy veto.)
  • Recurrence is the metric. The pass works when a known class does not recur; a repeat means the control was wrong, not that someone was careless. (CI4.)
  • The Diary is a narrative, not a source. Excluded from being re-ingested as promotable memory, or the corpus poisons itself. (OpenClaw.)

Starting points for the specification

The open decisions to resolve in /specify — each is a real fork, not a detail. Full discussion in open-questions.md.

  • Q1Where does the fleet store live? The pack (ships controls everywhere) vs. a learnings/ repo (lighter, prose) vs. both.
  • Q2What is the promotion oracle? Without a runtime Evaluator, how do we get a trustworthy “did it work?” — CI results, revert history, later-defect recurrence?
  • Q3How do we abstract instance → class safely? The value step, and the one most prone to over-generalising into false universals. Needs a rubric + human review.
  • Q4Cadence & trigger? Nightly vs. weekly vs. threshold (N new entries) vs. manual — likely a small per-repo policy, not a constant.
  • Q5Which runner? claude-cowork / OpenClaw / GitHub Action / cron differ in scheduling, session access, and model surface — verify with a spike, don’t assume.
  • Q6Does a model-in-the-loop job fit the pack’s stdlib-only identity? Ship the deterministic harness + prompts; leave the model call to the runner (as with CLI/doctor)?
Recommended first move: run /specify on “a /dream consolidation skill + a schedulable dream job + a federation layer,” citing this base. Then /adddomainexperts if the fleet spans unfamiliar domains, then /design. Because every guardrail is one the pack already holds, the design risk is low; the real work is Q2 (the oracle) and Q3 (safe abstraction).
