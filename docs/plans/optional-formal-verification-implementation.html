Optional Formal Verification: Implementation Plan

Summary

This plan explains how we get from the merged specification to a working feature.

  • Done: the contribution branch is set up, and a

proposed design is written and independently reviewed.

  • Waiting on Tim: the specification asks Tim to accept or revise its scope.

He has not done that yet, so implementation cannot start.

  • Next: open a draft PR from Lucio's fork so Tim can review the scope and

the proposed design together.

  • After Tim decides: run a small experiment to confirm that Verus works the

way the design assumes. Then finish the design and build the feature.

Nothing has been installed, run, or implemented yet.

Terms used in this plan

  • Verus: a tool that checks, mathematically, that Rust code meets a

written contract.

  • Contract: a precise statement of what a function must do, such as "accept

a range only if it fits inside the buffer."

  • Obligation: one claim the verifier is asked to check.
  • Proof Pack: AI-Forward's existing record of what was claimed, how it was

checked, and what risk remains.

  • Qualification experiment: a small, throwaway test that confirms one exact

Verus version works in one approved environment before we design around it.

  • Stale result: a verification result whose inputs (code, contract or tool

version) have changed since it ran, so it no longer counts.

Who Decides What

The specification is merged but not yet accepted. Its gate record says: "Human acceptance: Pending Tim's review. No implementation, toolchain installation, commit, push, or PR is authorized by this document." It also says /implement runs only "after the scope is approved and Verus is available in an approved environment."

Merging made the specification available to experiment with. It did not answer the four decisions the specification asks Tim to make:

  1. the opt-in boundary (verification stays off unless chosen);
  2. Verus as the first and only verifier;
  3. the evidence requirements;
  4. the worked example (a synthetic validator first; OpenVMM later, if at all).

Step 6: The Qualification Experiment

The goal is to learn whether Verus actually checks what the design assumes, before we build anything around it. It does not deliver the feature.

  1. Pick the environment. Record one approved operating system, Verus

version, Rust toolchain and solver. Do not assume Windows works just because this planning ran on Windows. Installing anything needs separate permission.

  1. Write the example. Use a tiny Rust function that checks whether a

requested range fits inside a buffer. Write its contract first, including which inputs are valid and which are rejected. The contract must require valid inputs to be accepted, so a function that rejects everything cannot pass.

  1. Set limits. Choose a time and resource limit before running. Check the

real Rust code, not a separate model of it.

  1. Run it both ways. The correct version must pass. Then introduce a

deliberate bug, such as changing <= to <, and confirm that it fails against the same, unchanged contract. A zero exit code or a "passed" count alone is not proof; confirm which obligations were actually checked.

  1. Record what happened. Keep the inputs, versions, command, output and

duration. If Verus was unavailable, unsupported or inconclusive, say so.

If the experiment cannot be completed, report it as blocked. Do not mark the design ready.

What the Finished Feature Must Do

These rows summarize the specification's acceptance criteria (FV-01 to FV-18 and UX-01 to UX-04).

CriteriaRequirement in plain terms
FV-01 to FV-03When verification is off, nothing changes: no Verus checks, installs or extra files. Declined, non-Rust and unsupported work is labeled as such.
FV-04 to FV-06Each claim links to a requirement and is written in English, with examples, assumptions and a named reviewer. If the meaning or the trusted assumptions change, the claim goes back for review.
FV-07 to FV-09Results use seven distinct outcomes: passed, failed, inconclusive, unavailable, unsupported, cancelled, not run. Timeouts, crashes, empty output and wrong-scope output are never reported as passed.
FV-10 to FV-12A result is current only if the code, contract, dependencies, tool versions and settings still match. A mismatch makes it stale; missing information makes it unknown. Old results are kept, not overwritten.
FV-13 to FV-15Existing tests and reviews still apply. No automatic uploads, installs, credential use or elevated permissions. No new mandatory review panel.
FV-16 to FV-18A live demo shows the correct example passing and the broken example failing. Tests cover unavailable tools, interruptions, empty checks and stale results, on every supported host.
Evidence storageAn interrupted write never looks like complete evidence. Two runs at once are refused rather than mixed.
UX-01 to UX-04Output shows the outcome and claim first, lists assumptions together, explains failures and next actions, and never implies the whole feature is approved.

Simulated test output checks the plumbing; it cannot replace the live demo.

Files Likely to Change

The design decides exact names. Expected areas:

  • existing /design-slice and /implement guidance, which loads formal

verification only when it is chosen;

  • a small helper script, only if the experiment shows one is needed;
  • the synthetic example and its tests;
  • the Proof Pack template and the code that reads it;
  • installation metadata and the generated copies of the pack.

Pack changes are made in pack/, follow /extendaibundle, update the revision notes, run pwsh tools/sync-pack.ps1 and pwsh tools/verify-bundle.ps1, and ship generated outputs in the same change. Rolling back turns the option off without deleting old evidence or existing checks.

Checks That Cannot Be Skipped

  • Tim's scope approval.
  • The required independent reviews, including any reviewer with veto power.
  • The test types required by the repository's Testing Strategy.
  • Tracing every changed file and every saved field to the code that reads it.
  • Seeing each new check fail before it passes (red-first).
  • Live Verus evidence, not just simulated output.
  • Audit and change-log entries.
  • Matching source and generated installations.
