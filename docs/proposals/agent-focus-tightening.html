Keeping extended-reasoning models on the task

A recommendation on how to tighten focus when models with extended reasoning (GPT-5.6 family and peers) keep adding unrequested tasks and ceremony — even after the reasoning level is reduced. Grounded in this repo's own /dream corpus and current (2025–26) industry research.

The one thing to take away. You are pulling the wrong lever. Reasoning effort controls how deeply the model thinks (overthinking); it does not control whether the model expands the task (scope creep). Those are two different failure modes on two different axes — which is exactly why turning the reasoning dial down does not stop the drift.

The problem, precisely named

The research literature separates two failure modes that feel similar and are routinely conflated:

Your symptomsecondarythis one — "additional tasks and ceremony"

The mechanism behind your symptom has a name: Latent Goal Crystallization — an agent's operative sub-goals mutate and the task expands without any explicit re-prompting (arXiv 2505.02709; 2601.04170). It is a task-adherence failure, not a reasoning-depth one.

Verified · this repo  The /dream pass over our own corpus (drm-0008) measured that 61 of 78 substantive turns (78%) recorded no goal-state / done_when. We already have the right control — the CT19 "goal · done-when · not-in-scope" opening — and it is skipped in the large majority of turns. The gap is enforcement, not missing directives. The literature predicts this exactly: standing prose instructions degrade under long context ("instruction-following degradation").

What the evidence says works

The 2025–26 literature converges on four levers for scope/task adherence — none of which is "reason less":

1 · Enforced "done" predicate

A pre-stated, checkable completion condition. Its absence is the single biggest cause of agents that stall or over-run.

2 · Adaptive anchoring

Periodically re-validate the work against the original goal, so accumulated context cannot silently redefine the task.

3 · Structured scope locks

System-prompt blocks, not prose: "implement exactly what's asked; surface improvements as optional text, never implement without approval; cap tool calls." (OpenAI GPT-5/5.1 guides.)

4 · Bounded self-critique

One targeted pass against the acceptance criteria, then stop. Unbounded, it becomes "degenerating reasoning" — non-terminating self-correction, i.e. MORE ceremony.

The meta-warning that governs every recommendation below. The failure mode is "too much unrequested work". Any fix that adds an unbounded self-review, a new heavyweight ceremony, or a persona that always convenes would increase the very thing you are trying to remove. Scope control must be cheap, structural, and self-terminating.

Your three questions

Q1

Should we extend the persona definitions?

Low leverage

Recommendation: No new persona. A small convene-trigger tweak, optionally.

Scope discipline is already owned — by the Simplifier (soft veto on unjustified complexity) and the Tech Lead (smallest correct change; reviewer findings are advice, not scope). A new "scope sentinel" persona would duplicate them. More importantly, personas convene at gates, not per turn — so they cannot catch per-turn scope creep as it happens; they fire too late to stop a runaway turn. The only cheap increment worth considering: sharpen the Simplifier/Tech-Lead convene trigger so it fires on any autopilot turn that touched more files than its stated scope — but that is a trigger tweak, not a persona extension.

Q2

Should we add more directives?

Low–medium leverage

Recommendation: No more prose. Instead, promote the one directive we have from prose to structure.

We are not short of directives. CT14–CT18 (capture ideas, don't chase them; smallest change; reviewer findings are advice), CT19–CT24 (the two-step goal-state front matter), GO1–GO18 (execution-graph planning with termination variants), and the registered PACK-O class already say everything the research recommends. Adding another paragraph to an always-loaded file that is already skipped 78% of the time is, in the pack's own words, "a memoir".

The high-value move hiding inside this question: take the goal-state opening and move it up the CI6 control ladder — from "always-loaded instruction" (rung 3, skipped) to a structural, mechanically-detectable opening (rung 2). We already log the done_when field and mine its absence (the PACK-O miner); the change is to make the opening a required shape rather than a requested habit.

Every non-trivial turn opens with, before the first substantive tool call:
  Goal:        <one line — the outcome the user asked for>
  Done when:   <a terminal condition you can point at and check>
  Not in scope: <what this turn will NOT touch>
A gap found en route is a finding (captured), never a new goal.
Q3

Should we create a session self-assessment?

Highest leverage — if bounded

Recommendation: Yes — a lightweight, bounded, self-terminating session self-assessment. This is the strongest of the three options.

The evidence is specific: self-critique reliably improves definition-of-done adherence when it is bounded (max one pass by default, prioritise floor/correctness failures over polish) and hurts (adds ceremony) when it is open-ended. So the self-assessment must itself obey the rule it enforces. Concretely, a single closing pass:

  • Restate the goal state written at the open (Q2). If none was written on a substantive turn → that is the finding (this is the PACK-O presence check we already log).
  • Map each output to the "Done when" — is each change traceable to the stated outcome? List anything that is not.
  • Scope diff — did the turn touch anything outside "Not in scope"? If so, was it required by the goal, or is it drift to revert / capture as a next step?
  • Stop. One pass. Do not re-plan, do not "improve" — name gaps and end with the existing Completed / Remaining / Next close (E18).

Crucially, most of the machinery already exists: the audit done_when field, the PACK-O miner, and the E18 close. A self-assessment mostly wires these into a single required closing step — and, because it maps to pre-stated criteria, it is bounded by construction.

And a note on the reasoning dial. Keep it as a separate control for overthinking (routine work → lower effort). It is genuinely useful — just for a different problem. It will not fix scope drift no matter how low you set it.

This proposal is analysis for your decision. Nothing here has been implemented — no persona was changed, no directive added, no self-assessment built. That is deliberate: implementing changes off a "what should we consider?" question would be the exact scope creep this document is about.
