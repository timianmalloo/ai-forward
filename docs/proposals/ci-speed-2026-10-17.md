# Proposal: make CI fast again without weakening the gate

**Date:** 2026-10-17 · **Author lens:** SRE & Systems Diagnostician (Adversary mode) · **Standard:** `ci-and-test-efficiency` (CE1–CE26) · **Tier:** T1

Every number carries a label. **Verified** means it was read from GitHub run data (`gh run list`, `gh run view --json jobs`, `gh api .../timing`) or from a local run. **Inferred** means it was modelled, and the model is stated next to it.

### Top 3 changes (ranked by minutes saved ÷ effort)

1. **Run pytest with `pytest-xdist -n auto` in every pack-consistency job** (C1). It cuts the 98% step by roughly 2.4–3× (Inferred). Effort is a one-line change plus a spike to prove the tests are parallel-safe. The same 1,854 tests run.
2. **Drop the duplicated pytest list from `adoption-entrypoints.yml`** (C2). The workflow keeps only what is unique to it: the real remote one-liner, the repeat install and the Windows `cmd` one-liner. Those 28 files are already gated three times by pack-consistency.
3. **Add `concurrency: cancel-in-progress` and a duration-budget control (CE26)** (C3 + C6). Superseded runs are cancelled, and the next 4× regression fails loudly in the week it lands, not when someone notices.

## 3. Regression finding

There are **two separate regressions**. They need different fixes.

**R1 — the step jump (PR #6, now `f92cf31` on main).** Between run 38981869532 (98d19b1) and run 38983040683 (4cdf355), on the same day, with no runner change:

| Job | Before | After | Δ | Factor |
|---|---|---|---|---|
| ubuntu pytest | 349 s | 801 s | +452 s | 2.3× |
| windows pytest | 666 s | 2,754 s | +2,088 s | 4.1× |
| macOS pytest | 314 s | 1,253 s | +939 s | 4.0× |

All Verified. PR #6 added or changed 35 test files (+8,140 lines, Verified with `git show --stat f92cf31 -- tests`). They include `test_bootstrap.py` (+1,092), `test_delivery_repair_history.py` (+857), `test_delivery.py` (+824), `test_upstream_adoption_integration.py` (+819), `test_delivery_outcome_repairs.py` (+759) and `test_delivery_startup_composition.py` (+662). These tests spawn processes heavily: for example, `test_pack_apply.py` has 24 spawn sites and 18 `git` invocations, and `test_delivery_startup_composition.py` has 24 spawn sites (Verified with grep). Windows has the worst factor (4.1×). That fits the known pattern that process creation and small-file I/O cost several times more on Windows runners (Inferred; the CE3 contention signature is not separately measured). The profile in section 3a names the slowest tests.

Main now contains `f92cf31` and `c267bd4`. **No pack-consistency run has been recorded on main since PR #6 landed** (Verified: the last main run is 38573757575, on 2026-10-14). The 46.8 min figure therefore comes from the PR #6 rebase branch whose tree became `f92cf31`. That it equals main today is Inferred.

**R2 — the creep.** Before PR #6, the ubuntu pytest step grew from 129 s (2026-09-20) to 349 s (2026-10-16): 2.7× in four weeks (Verified). The suite now holds 1,854 tests (Verified, `pytest --collect-only`). It runs serially (`pytest-xdist` is not installed; Verified). This is the CE26 class: per-item cost grows with the product, and nothing watches the aggregate.

## 4. Proposed changes, ranked by minutes saved ÷ effort

| # | Change | Saving per run | Effort | Ratio |
|---|---|---|---|---|
| C1 | `pytest -n auto` (pytest-xdist) in all three jobs | ~30 min wall, ~50 runner-min (Inferred) | S (one line per job + spike) | highest |
| C2 | adoption-entrypoints: stop re-running the 28 test files | 3 jobs × that subset (not measurable: the workflow never completed) | XS (delete one step) | high |
| C3 | `concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }` on pack-consistency, docs and adoption-entrypoints | One full run per superseded push (Inferred) | XS | high |
| C4 | Fix the slowest tests from the profile (shared fixture, fewer spawns) | Depends on profile | M | medium |
| C5 | Fold docs.yml `validate` and the pages `gate` into pack-consistency | ~20 s per push (Verified job sizes) | S | low |
| C6 | CE26 duration-budget control | Prevention, not saving | S | — (floor) |
| C7 | Re-enable push/PR triggers once C1 is green | Restores coverage | XS | — (floor) |

### C1 — parallelise pytest with pytest-xdist

- **Evidence.** pytest is 96.7–98.4% of every job (run 38983040683, Verified). The suite runs serially with 1,854 tests (Verified). GitHub-hosted standard runners for public repos have 4 vCPU on Linux and Windows (Inferred from GitHub's published runner specs; verify on use, CE8 note).
- **Saving.** Inferred, about 2.4–3× on the pytest step. Model: 4 workers, parallel efficiency 0.6–0.75 for a spawn- and I/O-bound suite. Windows 2,754 → ~920–1,150 s. macOS 1,253 → ~550–700 s (3 vCPU). ubuntu 801 → ~270–330 s. The run's wall-clock is bounded by Windows: ~16–20 min. With C4 it drops to ~12–15 min.
- **Risk.** Tests that share state can race: a fixed path under the repo, a shared `.git` config, `os.chdir`, or env mutation. A race under xdist is a real **finding** (PARALLEL-BLIND, CE22). Do not answer it with `-n 1`.
- **Coverage argument.** The same 1,854 tests run with the same assertions. Only the scheduling changes (CE10, CE14). Pin the worker count (`-n 4`, not only `auto`) so the shape is reproducible. Keep `-p no:randomly` behaviour unchanged. Assert in the step that the reported pass count equals the collected count, so a worker crash cannot hide tests (CE21).

### C2 — remove the duplicate test list from adoption-entrypoints

- **Evidence.** The step `Routing, resume, preservation and real deployment tests` names 28 files. All 28 are under `tests/docs_explorer/` and are collected by `pytest tests` in pack-consistency on ubuntu, windows and macOS (Verified by reading both workflows). The one difference: adoption-entrypoints installs `uv` and sets `AIF_TEST_OLD_PYTHON`, which some of those tests may need in order not to skip.
- **Saving.** Not measurable today: the workflow has never completed a job (Verified, `jobs: []`). Inferred: those files are the bulk of the R1 growth, so the step is plausibly 10–30 min per OS.
- **Risk.** If a test skips in pack-consistency because `uv` or the old Python is missing, removing it here loses that coverage. **Mitigation (required, not optional):** first add the `uv` install and the `AIF_TEST_OLD_PYTHON` export to the pack-consistency jobs, then show that the skip count of those files is 0 there, then delete the step here.
- **Coverage argument.** CE6, applied across workflows: the same tests on the same tree with the same environment are re-proving a green result. The unique proofs (the remote one-liner, the repeat install, the `cmd` one-liner) stay.

### C3 — concurrency cancel-in-progress

- **Evidence.** Only `pages.yml` declares `concurrency`, and it uses `cancel-in-progress: false` on purpose for deploys (Verified). Before 2026-10-04 pushes landed minutes apart. Runs 35513607572 (13:28), 35514067785 (13:37) and 35514952810 (13:56) overlapped (Verified).
- **Saving.** One superseded run per rapid push sequence (Inferred).
- **Risk.** On `main`, cancelling an older run leaves an older commit without a verdict. Scope the cancel to non-main refs: `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`. Keep `pages` as it is.
- **Coverage argument.** CE13. The newest commit is always fully gated.

### C4 — fix the slowest tests

- **Evidence.** Section 3a. Seven files (`test_bootstrap_preservation`, `test_delivery_outcome_repairs`, `test_delivery_repairs`, `test_delivery_startup_composition`, `test_delivery_repair_history`, `test_delivery`, `test_bootstrap`) each exceed 60 s locally at > 3.5–7.5 s per test (Verified lower bound).
- **Saving.** Inferred. If per-test setup in those seven files drops from about 4–7 s to about 1 s (build the fixture repo or install once per module, then copy it per test, CE15), most of R1's +2,088 s on Windows goes away. Model: R1 is attributed to these files because they are the PR #6 additions and the step jump coincides with PR #6. A per-file CI profile is still needed to confirm this.
- **Risk.** A changed fixture lifetime can couple tests. Use CE14 (shared fixture per module, assertions unchanged) and CE15 (build a template repo or venv once, then copy it).
- **Coverage argument.** Fixture-lifetime change only. The test bodies and assertions are untouched. Mutation-check a sample if a fixture is shared.

### C5 — fold the small duplicates

- **Evidence.** The docs.yml `validate` step and the pages `gate` job (`check-consistency.py`) repeat gates that pack-consistency runs (Verified). Each job costs 7–25 s (Verified).
- **Saving.** ~20–40 runner-seconds per push (Verified job sizes).
- **Risk.** The pages gate exists because of FR-062 (publication must depend on the gate *on the same commit*). Do **not** remove it unless deploy is made `needs:` the full gate in the same run. Lowest priority; it may not be worth the risk.
- **Coverage argument.** It is neutral only if publication still depends on a green gate on the same SHA.

### C6 — the duration-budget control (CE26)

- **Evidence.** The 4× jump in R1 was visible only because someone dispatched the run by hand. Nothing watches the trend (Verified: no step records duration).
- **Proposal.** Add a final `if: always()` job that reads `gh api .../runs/${{ github.run_id }}/jobs` and appends the per-job duration to the step summary. It **warns** when a job exceeds a stated budget (proposed budget: Windows pytest ≤ 900 s after C1) and **fails** when a job grows more than 50% against the trailing median of the last 10 main runs. The budget is stated in `pack/` so a raise is a reviewed diff.
- **Coverage argument.** It adds a control and removes none.

### C7 — restore automatic triggers

- **Evidence.** Since 2026-10-04 nothing runs on push (Verified, commit `156943d`). `required_status_checks` is absent (Verified in `AGENTS.md`). So the only protection is a developer remembering to run `verify-bundle.ps1`.
- **Proposal.** Once C1 shows the run at or under budget, restore `push: [main]` and `pull_request` on pack-consistency (with the earlier `paths:` filter, which is safe because no check is *required*; CE7). Do the same on docs and pages.
- **Coverage argument.** This is the change that **raises** coverage. Everything above exists to make it affordable.

## 6. Open questions and residual risks

- **Is 4cdf355's run representative of main?** Inferred. Main has no run since PR #6 landed. Phase 0 answers this.
- **Are the tests parallel-safe?** Unknown. Phase 1 answers it. Any race found is a defect to fix, never a reason to drop `-n`.
- **adoption-entrypoints has never completed a job.** Its true cost and its pass/fail state are unknown. Both PR runs stayed queued 14 days with no jobs (Verified). Possible causes, none confirmed: a fork-PR approval gate, or a runner label it could not get.
- **Re-open trigger 1 of `note-required-status-checks` has fired.** A second contributor (Alex Hutanu, the author of `f92cf31`) now lands work on main. Once the gate is fast, the decision not to require pack-consistency should be revisited. This is out of scope here; it is the Release Engineer's call.
- **Local and CI gate sets differ.** `verify-bundle.ps1` checks drift on `.github/knowledge`, `.grok` and `.agents` and runs `context-budget.py prefix --gate` and `skills --gate`. The ubuntu job does neither (Verified by reading both files). That is a CTRL-D shape, not a speed issue. Hand it to the Test Architect.
- **`|| true` on `pack-doctor.py --json`.** In "Coordination layer installed" the next line fails if the JSON is missing, so this is not a full mute. It is still a CE19 smell. Advisory.
- **Billing.** It is $0 while the repo is public. The ~328 min-equivalent applies only if the repo goes private.
- **Runner vCPU counts** are Inferred from GitHub's published specs. Confirm with `nproc` in the phase 1 spike.
